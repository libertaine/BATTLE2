# agent_scaffold

**Module:** `engine/src/battle_engine/agent_scaffold.py` (new)
**Purpose:** `bytefray agents create <agent-id>` — create the minimum
filesystem structure for a valid, discoverable Agent API v1 Python agent
under the writable Bytefray data root, without the author hand-copying
`docs/AGENT_AUTHORING.md`'s example.

## 0. Relationship to v0.4

This is **Phase 1** of v0.4's Agent Authoring & Development Feedback Loop
theme (`ARCHITECTURE.md`'s "v0.4 direction": create → validate → test →
inspect → modify → repeat). Phase 0 was documentation/packaging hygiene only
(see `CHANGELOG.md`'s `[Unreleased]` section) and landed no code. Nothing
this document describes is implemented yet; this is a specification only,
written before implementation per `CONTRIBUTING.md`'s spec → issue → prompt →
PR flow. Phase 2 (validation/dry-run of a created agent) and later phases
(`agents test` development matches, GUI creation, etc.) are explicitly out of
scope here and are not assumed to exist yet.

## 1. Purpose and non-goals

**Purpose.** Provide one CLI operation, `bytefray agents create <agent-id>`,
that:

- creates `<< get_data_root() >>/agents/<agent-id>/agent.yaml` and
  `agent.py` — a minimum, valid, immediately-discoverable Agent API v1
  Python agent — using the project's existing writable-data-root resolver
  (`battle_engine.paths.get_data_root`), never a reimplementation of
  `BYTEFRAY_ROOT`/`BATTLE2_ROOT`/`BATTLE_ROOT` fallback logic;
- is non-destructive: it never overwrites an existing agent directory, an
  existing non-directory file at that path, or any other pre-existing user
  data;
- produces output that `battle_engine.agents.discover_agents` and
  `battle_engine.agent_api.load_python_agent` accept immediately, with no
  process restart, extra "activation" step, or manual manifest editing
  required before the agent can be selected by `bytefray run --a-type
  <agent-id>` or discovered by `bytefray agents`;
- is deterministic: the generated bytes are identical on every invocation
  for a given `<agent-id>` (in fact, per §7, identical across *every*
  `<agent-id>` — see below), with no timestamps, random content, or
  environment-dependent text baked into the generated files;
- is usable from a headless installation (no GUI, no network access, no
  interactive prompts).

**Non-goals** (see also §12, "Explicitly out of scope"):

- Validating that the generated agent actually plays a full, error-free
  match — that is Phase 2's `agents validate`/dry-run work, not this
  command's job. This command's only correctness obligation is "the files
  it writes parse and load," which is covered by reusing
  `discover_agents`/`load_python_agent` directly in its own tests (§11),
  not by re-simulating a match.
- A general-purpose project/file generator framework. This command has
  exactly one output shape (§5) and no template selection, prompts, or
  configuration surface in this phase.
- `--force`/overwrite semantics, multiple template families, LLM
  generation, Redcode scaffolding, or Agent API v2 — see §12.

## 2. Existing building blocks this spec reuses

Inspected before writing this spec (all under `engine/src/battle_engine/`
unless noted):

- **`paths.py`** — `get_data_root(environ=None)` is the sole writable-root
  resolver. It already implements the documented `BYTEFRAY_ROOT` →
  `BATTLE2_ROOT` → `BATTLE_ROOT` fallback chain (`configured_data_root`),
  falling back to a source checkout, a frozen application's executable
  directory, or the platform-installed default. This spec's command calls
  `get_data_root()` directly and must not re-derive or shadow this logic.
- **`agents.py`** — `discover_agents(root)` / `discover_agents_in(base)`
  scan `<root>/agents/*` and build an `AgentSpec` per subdirectory that has
  `agent.yaml` and/or `agent.py`; `_spec_from_dir` infers `kind: python`
  automatically when `agent.py` exists and no explicit `kind` is given, and
  infers `entrypoint: agent.py:create_agent` the same way. `resolve_agent
  (root, name)` additionally enforces that a caller-supplied name resolves
  *within* `<root>/agents` (via `.resolve()` + `Path.relative_to`), a
  containment check added specifically because a manifest's own declared
  `name` field was once usable to escape the agents tree (regression test:
  `test_resolve_agent_rejects_a_name_that_escapes_the_agents_directory` in
  `engine/tests/test_agent_api.py`). §4 reuses this same containment
  pattern for the *directory name the caller passes on the command line*,
  and deliberately avoids writing a `name` field into the generated
  manifest at all, so a generated agent's on-disk identity and any manifest
  self-declaration can never disagree (see §6).
- **`agent_api.py`** — `load_python_agent` hard-requires
  `agent_spec.api_version == AGENT_API_VERSION` (currently `1`); everything
  else it needs (`entry_point`, `kind`) can be either explicit in the
  manifest or inferred by `_spec_from_dir` from `agent.py`'s presence.
  `parse_entry_point` independently re-validates that the entry point stays
  within the agent directory. The loader requires the factory to return an
  object with callable `reset(context)`/`act(observation)`.
- **`starters.py`** — `ensure_starter_agents()` is the existing
  "install bundled resource files into the writable catalog, skipping any
  file that already exists" pattern (`open(destination, "xb")`, i.e.
  exclusive-create — `FileExistsError` is caught and treated as "already
  present, skip," not an error). It is idempotent and safe to call
  repeatedly. Its four bundled starters (`runner`, `writer`, `seeker`,
  `spiral`, `battle_engine/data/starter_agents/<name>/agent.yaml`) are
  **all manifest-only VM built-ins** — none has an `agent.py`, none is
  `kind: python`. There is therefore no existing bundled *Python* agent
  template to copy or adapt; see §8 for what this means for "relationship
  to bundled starters."
- **`battle_engine/command.py`** — the `bytefray`/`battle2` top-level
  dispatcher. `agents` is currently one of five hand-rolled subcommands
  (`COMMANDS = ("run", "tournament", "replay", "design", "agents")`), each
  a plain function taking the remaining `argv`, not a nested `argparse`
  subparser tree. `_agents(argv)` today accepts **only** `[]`, `["--help"]`,
  or `["-h"]` — any other argv (including a bare positional) currently hits
  `parser.error("unrecognized arguments: ...")` and exits 2. It forwards to
  `battle_engine.cli.main(["--list-agents"])`, which itself calls
  `ensure_starter_agents()` before `discover_agents()` so starters always
  exist before listing.
- **Tests inspected:** `engine/tests/test_agent_api.py` (manifest/
  discovery/loading contract, containment regression tests),
  `engine/tests/test_starter_agents.py` (non-destructive copy idiom,
  Windows-path-with-spaces coverage, frozen/installed root coverage),
  `engine/tests/test_paths.py` (root-resolution precedence),
  `engine/tests/test_battle2_command.py` (subcommand dispatch, `--help`
  conventions, `test_agents_command_initializes_starters_idempotently`
  showing the existing subprocess-based CLI test idiom for the `agents`
  command).

## 3. Command/API surface

### 3.1 Exact CLI syntax

```text
bytefray agents create <agent-id>
```

with `battle2 agents create <agent-id>` behaving identically (the existing
`battle2_main` deprecation-notice wrapper already applies uniformly to every
subcommand; no special-casing needed).

### 3.2 Why a nested verb inside the existing `agents` command, not a new top-level command or a full `argparse` subparser tree

- `COMMANDS` and `_parser()` in `command.py` model *top-level* command
  identity (`run`, `tournament`, `replay`, `design`, `agents`); `create` is
  an operation *on* the agent catalog, the same conceptual level as the
  existing bare-`agents` "list" behavior, not a sibling of `agents` itself.
  A new top-level `bytefray create` would misrepresent that relationship
  and would collide with `bytefray agents`'s existing sole ownership of
  agent-catalog concerns.
- Every existing subcommand (`_design`, `_agents`, and `tournament`/`replay`
  by delegation) is a **hand-rolled `argv` dispatch function**, not a nested
  `argparse` subparsers object — `_agents` today does a manual `argv ==
  ["--help"]` / `argv == ["-h"]` / `if argv: parser.error(...)` sequence
  rather than building an `add_subparsers()` tree. Introducing a full nested
  `argparse` subparser tree for one new verb, when no existing top-level
  command uses that pattern, would be the larger, less consistent change.
  The smallest change consistent with the current architecture is: extend
  `_agents(argv)` to recognize a leading `"create"` token and delegate the
  remainder to a dedicated module's own `main(argv)`, exactly as `_agents`
  already delegates whole-command handling to `battle_engine.cli.main` and
  `_tournament` delegates to `battle_engine.tournament_cli.main`.
- Concretely, `command.py`'s `_agents` becomes:

  ```python
  def _agents(argv: list[str]) -> int:
      if argv and argv[0] == "create":
          from battle_engine.agent_scaffold import main as scaffold_main
          return scaffold_main(argv[1:])
      if argv == ["--help"] or argv == ["-h"]:
          return _simple_help("agents", ...)  # mentions both list and create
      if argv:
          parser = argparse.ArgumentParser(prog="bytefray agents", add_help=False)
          parser.error(f"unrecognized arguments: {' '.join(argv)}")
      from battle_engine.cli import main as engine_main
      return engine_main(["--list-agents"])
  ```

  Bare `bytefray agents` and `bytefray agents --help`/`-h` are **unchanged**
  in behavior — existing tests
  (`test_agents_command_initializes_starters_idempotently`,
  `test_every_subcommand_help_works_without_launching_optional_ui`,
  `test_every_subcommand_help_uses_bytefray_prog`) keep passing unmodified.
  `_agents`'s help text should be updated to mention `create` exists, but
  that is a one-line documentation change, not a contract change.

- `battle_engine.agent_scaffold.main(argv)` owns its own tiny `argparse`
  parser (`prog="bytefray agents create"`, one required positional
  `agent_id`, no other arguments in this phase — see §12 on `--force`),
  mirroring the shape of `battle_engine.tournament_cli._parser()`. This
  keeps the new module independently testable and independently
  `--help`-able, consistent with every other delegated subcommand.

### 3.3 Exit codes

| Condition | Exit code |
|---|---|
| Agent created successfully | `0` |
| `--help`/`-h` | `0` |
| Missing/extra positional arguments (argparse usage error) | `2` (argparse's own convention, matching every other subcommand's `parser.error` exit code) |
| Invalid `agent-id` (§4) | `2` |
| Duplicate `agent-id` — directory, file, or any entry already exists at the destination (§5) | `2` |
| Data root exists but is not writable / OS error creating the directory or files | `2` |

`2` is used uniformly (not a distinct code per failure category) because
that already matches this CLI's existing convention: `run`'s unknown-agent
and bad-argument paths, `tournament`'s configuration-error path, and
`_agents`'s own `unrecognized arguments` path all currently exit `2` for
any user-correctable input/environment problem, reserving `0` for success.
Introducing a finer-grained exit-code taxonomy for this one subcommand
would be inconsistent with the rest of the CLI and is not justified by any
concrete downstream consumer (no tooling in this repository branches on a
distinct non-zero code today).

### 3.4 stdout/stderr behavior and successful output

- All diagnostics (usage errors, duplicate-ID errors, I/O errors) go to
  **stderr**, matching every other error path in `cli.py`/`tournament_cli.py`
  (`print(..., file=sys.stderr)` or `argparse`'s own stderr usage output).
  Nothing is printed to stdout on failure.
- On success, stdout prints the created agent's identity and the paths
  written, in the same `label: path` shape `cli.py`'s own successful-match
  output already uses (`result: <path>`, `replay: <path>`, `summary:
  <path>` — see `test_single_match_output_names_canonical_and_
  compatibility_artifacts`), for consistency and easy scripting/grepping:

  ```text
  agent: <agent-id>
  manifest: <data_root>/agents/<agent-id>/agent.yaml
  source: <data_root>/agents/<agent-id>/agent.py
  ```

  A closing hint line naming the immediate next step is useful and cheap:

  ```text
  Run 'bytefray run --a-type <agent-id> --b-type <opponent>' to try it.
  ```

  No progress/spinner output; this operation is a handful of filesystem
  writes and completes essentially instantly.

## 4. Agent ID rules

**Current effective constraints, as implemented today:** none, beyond what
the filesystem and `resolve_agent`'s containment check enforce.
`discover_agents_in` accepts *any* subdirectory name the OS allows and that
contains `agent.yaml`/`agent.py`; `resolve_agent` only rejects a name whose
resolved path escapes `<root>/agents` (the `../outside/payload`-style
attack covered by `test_resolve_agent_rejects_a_name_that_escapes_the_
agents_directory`). There is **no existing normalization convention** —
directory names are used exactly as given, byte-for-byte, as both the
discovery key and the CLI selector string (`--a-type`/`--b-type`). Per this
task's instruction to prefer rejecting ambiguous input over inventing a new
normalization convention, the scaffolder introduces a **stricter allow-list**
than raw discovery requires, rather than normalizing (lowercasing,
slugifying, trimming) a user-supplied ID:

- **Accepted characters:** ASCII letters, digits, hyphen (`-`), and
  underscore (`_`) only, expressed as `^[A-Za-z0-9][A-Za-z0-9_-]*$`. No path
  separators (`/`, `\`), no `.`, no leading digit-only restriction beyond
  requiring the first character to be alphanumeric (rules out a leading
  `-`/`_`, which some shells and flag parsers mistreat as an option).
- **Length:** a generous but bounded cap (e.g. 64 characters) — long enough
  for any realistic agent name, short enough to avoid `MAX_PATH`-adjacent
  Windows path-length pitfalls once nested under a deep `BYTEFRAY_ROOT`.
- **Normalization:** **none.** The ID is used exactly as typed for the
  directory name. This is a deliberate difference from "rewrite it to be
  safe" behavior: an ID that isn't already valid is rejected with a clear
  message rather than silently coerced into a different ID than the one the
  user typed (which could otherwise surprise a caller scripting around the
  command, or collide with an existing directory the user didn't expect).
- **Case sensitivity:** names are compared and stored byte-for-byte, exactly
  as `discover_agents`/`resolve_agent` already treat directory names
  elsewhere — no case-folding. (Whether two IDs differing only by case
  collide is then purely a question of the *host filesystem's* case
  sensitivity, same as any other two same-named-except-case directories;
  this command does not add its own case-insensitive duplicate check on top
  of the filesystem's own behavior.)
- **Path traversal prevention:** enforced twice, defense-in-depth, both
  before any filesystem write:
  1. The allow-list regex above already excludes `/`, `\`, and `.. ` cannot
     be formed from `[A-Za-z0-9_-]` alone, so a traversal sequence cannot
     pass the regex at all.
  2. As a second, independent check (reusing the exact pattern
     `resolve_agent` already uses): resolve `agents_dir / agent_id` and
     confirm the result is still `agents_dir / agent_id` exactly (or at
     minimum, resolves *within* `agents_dir` via `Path.relative_to`) before
     creating anything. This guards against any future weakening of the
     regex and keeps the two containment checks in the codebase
     (`resolve_agent`'s read-side check, this write-side check) provably
     consistent with each other rather than independently invented.
- **Reserved/conflicting names:** **no additional reserved-word list beyond
  the allow-list and the ordinary duplicate-directory check (§5).** Built-in
  VM agent names (`runner`, `writer`, `bomber`, `flooder`, `spiral`,
  `seeker` — `battle_engine/builtins/registry.py`'s `SUPPORTED`) are
  **not** filesystem-reserved today: existing discovery already lets a
  directory under `agents/<name>/` shadow a same-named built-in (this is
  exactly how the four manifest-only starters already work — `agents/
  runner/` is a real directory that `resolve_agent` finds and prefers over
  the compiled-in `runner` bytecode). Reproducing that precedent, creating
  `bytefray agents create runner` is allowed by ID validation and will
  simply hit the **ordinary duplicate-directory rejection** in §5 (because
  `ensure_starter_agents` already populated `agents/runner/agent.yaml`
  before any `bytefray agents ...` invocation reaches this command — see
  §9). Creating `bytefray agents create bomber` or `...flooder` (built-ins
  with **no** starter directory) would succeed and would shadow the
  built-in the same way; this is accepted, pre-existing discovery behavior,
  not a new risk this command introduces, and adding a bespoke reserved-word
  list here would be inconsistent with how `resolve_agent`/`_resolve_agent`
  already treat that overlap everywhere else in the CLI.
- **Invalid ID behavior:** reject before touching the filesystem at all
  (before even calling `get_data_root()`'s consequences, i.e. before
  `mkdir`), with a stderr message that states the allow-list plainly (e.g.
  `"Invalid agent id 'foo/bar': must match ^[A-Za-z0-9][A-Za-z0-9_-]*$
  (max 64 characters)."`) and exit code `2`.

## 5. Destination

- **Canonical destination root:** `battle_engine.paths.get_data_root() /
  "agents"` — identical to `agents._agents_root`'s own `(root /
  "agents").resolve()`, computed via the shared resolver, never
  reimplemented.
- **Resulting path:** `<data_root>/agents/<agent-id>/agent.yaml` and
  `<data_root>/agents/<agent-id>/agent.py`.
- **If the root does not yet exist:** created with `mkdir(parents=True,
  exist_ok=True)`, identical to `ensure_starter_agents`'s existing
  `agents_dir.mkdir(parents=True, exist_ok=True)` call — no special
  first-run ceremony.
- **If the agent directory already exists (with any content — a prior
  agent, an empty directory, or unrelated files):** rejected. Exit `2`,
  stderr names the existing path and states that it was not modified. No
  file inside it is read, written, or deleted. This is the "duplicate ID"
  case; there is no `--force` (see §12) and no partial/merge behavior — the
  entire operation is refused up front once the destination directory is
  found to already exist.
- **If a non-directory file already exists at
  `<data_root>/agents/<agent-id>`** (e.g. a stray file, not a directory):
  also rejected with the same "already exists" handling — no distinction is
  drawn between "a directory is there" and "a file is there" from the
  user's point of view; both mean the requested path is unavailable.
- **Default behavior is non-destructive** in every branch above: the only
  filesystem mutations this command ever performs are (a) creating
  `agents/` itself if absent, and (b) writing the two new files into a
  brand-new `agents/<agent-id>/` directory it created in the same call.

## 6. Generated `agent.yaml`

Minimum manifest, every field justified against the current implementation
inspected in §2:

```yaml
kind: python
api_version: 1
entrypoint: agent.py:create_agent
version: "0.1.0"
```

| Field | Required by current loader? | Justification for inclusion |
|---|---|---|
| `kind: python` | No — `_spec_from_dir` infers `"python"` automatically once `agent.py` exists and no `kind` is given. | Included anyway: it is the field `_spec_from_dir` *validates* strictly when present (`must be one of: builtin, blob, python`), and making it explicit means a later edit that removes or renames `agent.py` fails loudly (wrong `kind`/missing source) instead of silently reclassifying the agent as `kind: builtin`. Low cost, meaningfully more legible/defensive for a hand-edited file. |
| `api_version: 1` | **Yes** — `load_python_agent` raises `UnsupportedAgentAPIVersionError` unless this equals `AGENT_API_VERSION` (currently `1`). | Hard requirement; omitting it makes the generated agent unloadable. |
| `entrypoint: agent.py:create_agent` | No — inferred identically when omitted (same default string). | Included anyway: this is the one line that visibly wires the manifest to the source file and factory function; leaving it implicit would make the manifest look incomplete/mysterious to a new author and would be the wrong thing to omit from a file whose whole purpose is to be a legible starting point. |
| `version: "0.1.0"` | No — `AgentMetadata.version` defaults to `agent_spec.version or "0"` when absent. | Included as a low-cost, obviously-meaningful placeholder an author would otherwise have to add themselves the first time they care about it; `"0"` (the silent default) is a less informative starting value than an explicit, conventional `"0.1.0"`. |

**Deliberately omitted, with reasoning:**

- **`name`** — not required for discovery or loading (agent identity is
  always the directory basename per `test_discovered_spec_name_is_always_
  the_directory_basename`; a manifest's own `name` is inert free-text
  metadata, only ever echoed back, never authoritative). Including a `name`
  field that merely duplicates the directory name adds a second, unenforced
  copy of the identity that can drift if the directory is later renamed,
  and echoes exactly the field shape
  (`test_resolve_agent_rejects_a_name_that_escapes_the_agents_directory`)
  that was once a real path-traversal vector when *other* code trusted a
  declared `name` over the real directory. Leaving it out entirely avoids
  recreating that pattern in newly-generated files.
- **`display`** — not required; `_spec_from_dir` already falls back to
  `meta.get("display") or meta.get("name") or name`, i.e. the directory
  basename, when absent — identical listing behavior with or without it.
  Omitted for the same "avoid a second, driftable copy of the name" reason
  as above.
- **`defaults`** — this dict is specific to built-in/blob agents' VM
  parameter overrides (`--byte`, `--offset`, `--stride`, etc., consumed by
  `battle_engine.builtins.build_agent`); a Python agent has no equivalent
  consumer for it. An empty `defaults: {}` would be dead, unjustified
  content.
- **`description`** — parsed into nothing; `_spec_from_dir` never reads a
  `description` key (only `display`/`name`/`defaults`/`api_version`/
  `version`/`entrypoint`/`kind` are inspected — see `agents.py`). Any value
  here is unused decoration, which the task's "do not write fields merely
  because they might be useful someday" instruction rules out.

## 7. Generated `agent.py`

**Approved revision (supersedes the `HALT` draft below the line):** the
placeholder action is `WRITE`, not `HALT` — see the resolution of design
decision 3 in §13. `HALT` would satisfy every structural requirement in
this section but would not show a new author what an ordinary, valid,
state-changing action looks like, which is the actual point of a
starting-point template. `WRITE` is directly supported by Agent API v1,
requires only the two extra fields (`operand`, `value`) already documented
in `docs/AGENT_API_V1.md`'s action vocabulary table, and keeps the template
in sync with `docs/AGENT_AUTHORING.md`'s existing hand-written example
(§13 decision 2's own reasoning for avoiding unnecessary drift between the
doc example and the generated template applies equally here).

```python
"""Starting point for a Bytefray Agent API v1 agent."""

from battle_engine.agent_api import ActionKind, AgentAction, MatchContext, Observation


class Agent:
    def reset(self, context: MatchContext) -> None:
        # Called once before tick 0. Save whatever state your strategy needs.
        self.rng = context.rng

    def act(self, observation: Observation) -> AgentAction:
        # Called once per tick; must return exactly one AgentAction.
        # Strategy goes here. This starting point writes a fixed byte to a
        # random address using the match's deterministic per-entrant RNG.
        address = self.rng.randrange(256)
        return AgentAction(ActionKind.WRITE, address, 0xA5)


def create_agent() -> Agent:
    return Agent()
```

- **Imports only what a normal user agent is expected to import:**
  `battle_engine.agent_api`'s public, documented surface
  (`ActionKind`, `AgentAction`, `MatchContext`, `Observation`) — the same
  four names `docs/AGENT_AUTHORING.md`'s own example imports. Nothing
  engine-internal (no `battle_engine.core`, `battle_engine.vm`, etc.).
- **Implements the required callable surface exactly:** `reset(self,
  context: MatchContext) -> None` and `act(self, observation: Observation)
  -> AgentAction`, matching the `AgentV1` protocol `load_python_agent`
  structurally validates (`missing = [name for name in ("reset", "act") if
  not callable(...)]`).
- **Deterministic under the API/RNG contract:** `act` draws from
  `self.rng` (`context.rng`, captured in `reset`), the engine-created,
  per-entrant `random.Random` instance whose seed is derived deterministically
  from the match seed, slot, and Agent API version (`docs/AGENT_API_V1.md`'s
  "Lifecycle" section). The template never reads a non-deterministic source
  (no `random.random()`, no wall-clock, no OS entropy), so behavior is
  identical across repeated runs of the same match seed, exactly the
  "deterministic under the supplied API/RNG contract" requirement in §1 —
  determinism here means "reproducible given a seed," not "constant."
- **Returns a valid action:** `WRITE` (`operand` the wrapped address,
  `value` the byte, per the Action vocabulary table in
  `docs/AGENT_API_V1.md`) is an ordinary, unattributed battlefield write —
  not a forfeit, not an exception, not an "invalid action" — so a fresh
  scaffold immediately participates in a match correctly. Writing a fixed
  byte to a random address is the "intentionally uncompetitive" baseline
  the product goal calls for: it does nothing strategic (no targeting, no
  reading, no reacting to `observation`), but it demonstrates the actual
  shape of a charged, state-changing action a real strategy will build on.
- **Concise comments, no tutorial text:** three one-line comments mark
  exactly the three places a new author needs (`reset`'s purpose, `act`'s
  cardinality contract, and — most importantly — the one line to replace).
  No paragraph-length docstrings, no restating the whole Agent API v1
  contract inline (that lives in `docs/AGENT_API_V1.md`, one link away via
  `docs/AGENT_AUTHORING.md`).
- **No per-agent-id substitution.** Because §6 omits `name`/`display` and
  this file contains no agent-id-derived content either, the generated
  `agent.py` (and `agent.yaml`) are **byte-identical across every
  `<agent-id>`** — only the *directory name* they are written into differs.
  This is a deliberate simplification: the "template" is a pair of static
  resource files copied verbatim (§8), not a string-rendered template with
  substitution logic, parameters, or an escaping surface to get wrong.

## 8. Relationship to bundled starters

**Decision: option 2 — a dedicated canonical template, not an adaptation of
an existing starter, sharing only the low-level "exclusive-create a copied
file" idiom with `starters.py`.**

This is essentially forced by what already exists, not a stylistic
preference: as established in §2, all four bundled starters
(`battle_engine/data/starter_agents/{runner,writer,seeker,spiral}/`) are
**manifest-only VM built-ins** — none has an `agent.py`, none is `kind:
python`. There is no existing "minimal Python agent" resource anywhere in
the repository to copy or adapt; the only prior art is the *documentation*
example in `docs/AGENT_AUTHORING.md`, which this spec's template
intentionally matches in spirit (same four imports, same `reset`/`act`
shape, same `create_agent()` factory name) so the two don't drift into two
independently-maintained "this is what a minimal agent looks like"
definitions.

- **Template resource location:** a new bundled resource directory,
  `engine/src/battle_engine/data/agent_template/`, holding the exact static
  `agent.yaml` and `agent.py` shown in §6/§7. This sits beside `data/
  starter_agents/` under the existing `battle_engine/data/**/*` package-data
  glob (`pyproject.toml`'s `[tool.setuptools.package-data]` already includes
  `"data/**/*"` for the `battle_engine` package) — **no `pyproject.toml`
  change is required** to ship it in the wheel or a frozen build; it is
  covered by the existing glob.
- **Resource-root lookup:** reuse `battle_engine.paths.get_resource_root()`
  exactly as `starters._starter_resource_dir` does, so source-checkout,
  installed-wheel, and frozen-application resource lookup all behave
  identically to the already-shipped starter-agent lookup (including its
  two-candidate-path fallback for a source checkout vs. an installed
  package layout).
- **Copy mechanism:** the same exclusive-create idiom `ensure_starter_agents`
  already uses (`destination.open("xb")`, `shutil.copyfileobj`), reused as a
  small private helper (a handful of lines) rather than imported from
  `starters.py` — the two callers have genuinely different failure
  contracts (`ensure_starter_agents` treats "file already exists" as
  "already installed, skip" and always succeeds; agent creation treats *the
  destination directory already existing* as an error to reject outright,
  per §5). Sharing the five-line "open exclusive, copy bytes" primitive
  between two call sites is not worth extracting into a shared utility
  function for only two callers with different surrounding error handling;
  it is fine to have two small, obviously-similar copies. If a third
  "install a static resource file into the writable root" caller appears in
  a later phase, that would be the point to reconsider extracting a shared
  helper — not now.
- **What is explicitly *not* shared:** `ensure_starter_agents`'s multi-file,
  multi-name, always-idempotent-skip behavior. Agent creation is
  single-directory, single-shot, and duplicate-rejecting (§5) — a
  meaningfully different contract that would only be obscured by forcing it
  through the same function.

## 9. Discovery and immediate usability

Immediately after a successful `bytefray agents create <agent-id>` returns
`0`, all of the following already hold, with **no process restart, cache
invalidation, or extra step**, because nothing in this codebase caches
agent-discovery results across process invocations — `discover_agents`
performs a fresh `base.iterdir()` scan every time it is called:

- `bytefray agents` (bare) lists `<agent-id>` — it calls
  `discover_agents(root)` fresh, and the new directory is a normal entry
  like any hand-authored agent.
- `bytefray run --a-type <agent-id> --b-type <opponent>` resolves and loads
  it through the existing `resolve_agent`/`load_python_agent` path — no
  special-casing needed, since the generated files satisfy the ordinary
  Python-agent discovery/loading contract by construction (§6/§7 are
  written specifically to satisfy `_spec_from_dir` and `load_python_agent`).
  `<opponent>` must itself resolve to a `kind: python` agent too (mixed
  VM/Python matches are unsupported per `AGENT_AUTHORING.md`) — that
  existing constraint is unrelated to and unaffected by this command; a
  fresh scaffold cannot usefully be matched against a VM built-in without a
  second Python agent already present or itself just created.
- `bytefray tournament <agent-id> <other-python-agent> ...` resolves it the
  same way via `tournament_cli._resolve_entrant`.
- The optional PySide6 Designer's `app.services.agent_catalog.AgentCatalog`
  also discovers it on its next scan, since it too is built on
  `discover_agents`/directory scanning (confirmed already exercised by
  `test_starter_agents.py`'s `test_every_starter_parses_and_designer_
  catalog_discovers_it` pattern for the starter case) — though Phase 1 adds
  no GUI-side affordance to *invoke* creation from the Designer; only the
  CLI is in scope (see §12).

## 10. Failure behavior

| Scenario | Behavior |
|---|---|
| Duplicate ID (directory or file already exists at the destination) | Rejected before any write; exit `2`; stderr names the existing path; nothing under `agents/<agent-id>/` is touched. See §5. |
| Invalid ID (fails the §4 allow-list, or the write-side containment re-check) | Rejected before any write, including before `agents/` itself is created if it didn't already exist; exit `2`; stderr states the allow-list. |
| Unwritable data root (`agents/` cannot be created, or the two files cannot be written — e.g. read-only filesystem, permission denied) | The underlying `OSError`/`PermissionError` is caught at the top level and reported as a plain stderr message (mirroring `ensure_starter_agents`'s and `_agents`'s own `except (FileNotFoundError, OSError, ValueError) as exc: print(f"ERROR: ...", file=sys.stderr); return 2` pattern) — no raw traceback. |
| Partial creation failure (e.g. `agent.yaml` write succeeds, `agent.py` write then fails) | Prevented by construction, not by cleanup-after-the-fact: both files are written into a **temporary sibling directory first**, then the whole directory is published in one `os.rename` (or `Path.replace`) once both files exist — see below. If the temp-directory build step itself fails partway, the incomplete temp directory is removed and the real `agents/<agent-id>/` destination is never touched at all, so a failed run can never leave a half-created, valid-looking-but-broken agent directory at the real path. |
| Unexpected I/O failure during the final rename itself | Extremely unlikely (rename of an already-fully-written temp directory) but still caught and reported the same way as any other `OSError`; the temp directory is left in place rather than silently deleted, so no user data is lost, and its non-standard name (see below) means `discover_agents` never mistakes it for a real agent. |

**Atomicity approach — simple temp-directory + rename, not a general
transactional filesystem layer** (per the task's explicit "do not
overengineer" guidance):

1. Validate `agent_id` (§4) — no filesystem touched yet.
2. Resolve `agents_dir = get_data_root() / "agents"`; `mkdir(parents=True,
   exist_ok=True)`.
3. Check `agents_dir / agent_id` does not already exist (§5); if it does,
   fail now, before creating anything.
4. Create a temporary sibling directory under `agents_dir` with a name that
   cannot collide with a real agent ID and that `discover_agents` would
   never treat as one even if left behind (the §4 allow-list already
   forbids a leading `.`, so a name like `.tmp-<agent_id>-<uuid4 hex>` is
   guaranteed distinct from every valid real agent directory and is
   automatically skipped by any future directory listing that only expects
   allow-list names). Write `agent.yaml` and `agent.py` into it (copied
   from the bundled template, §8).
5. `os.rename(temp_dir, agents_dir / agent_id)` — this is atomic on both
   NTFS and POSIX filesystems when source and destination share a
   filesystem/volume (true here, since both are directly under the same
   `agents_dir`), which is the same "temp-file-then-rename" discipline
   already used elsewhere in this codebase for atomic publication
   (`battle_engine.result_model.write_json_atomic`,
   `NativeMatchService`'s replay-publication step, both cited in
   `ARCHITECTURE.md`) — reusing an established pattern rather than
   inventing a new one.
6. On any exception during steps 4–5, remove the temp directory (best
   effort) and re-raise/report; the real destination path was never created
   or was only ever the atomic rename's target, never partially populated.

This is intentionally *not* a general rollback/transaction system — it is
exactly the two-step "build somewhere safe, then one atomic rename" shape
the task's own "temp-directory + rename semantics are sufficient" guidance
calls for, matching this repository's existing atomic-publish idiom rather
than adding a new one.

## 11. Required tests

Location: `engine/tests/test_agent_scaffold.py` (co-located with the other
`battle_engine` CLI/catalog test modules; no `gui` marker).

**Successful creation**
- Creating a fresh `<agent-id>` under an empty `tmp_path` data root writes
  exactly `agents/<agent-id>/agent.yaml` and `agents/<agent-id>/agent.py`,
  returns exit code `0`, and prints the `agent:`/`manifest:`/`source:`
  lines from §3.4 with the correct resolved paths.
- The generated `agent.yaml` and `agent.py` byte content matches exactly
  across two different valid `<agent-id>` values (confirms §7's
  "byte-identical template, only the directory differs" determinism claim).
- Calling the command twice in a row with two different valid IDs against
  the same data root succeeds both times and leaves both agents present.

**Generated file content/contract**
- The generated manifest parses via `battle_engine.agents.discover_agents`
  (or `discover_agents_in`) into an `AgentSpec` with `kind == "python"`,
  `api_version == 1`, `entry_point == "agent.py:create_agent"`, `version ==
  "0.1.0"`.
- `battle_engine.agent_api.load_python_agent(spec)` succeeds against the
  discovered spec and returns an instance whose `reset`/`act` are callable;
  calling `reset(context)` then `act(observation)` with a minimal
  hand-built `MatchContext`/`Observation` returns an
  `AgentAction(ActionKind.WRITE, operand, value)` with `operand` in
  `range(256)` and `value == 0xA5` (per §7's approved revision).
- The generated manifest contains none of the deliberately-omitted fields
  from §6 (`name`, `display`, `defaults`, `description` are absent).

**Immediate discovery**
- After creation, `discover_agents(data_root)` includes `<agent-id>` in the
  same process, with no extra setup call (confirms no caching/staleness).
- An end-to-end subprocess test (mirroring
  `test_agents_command_initializes_starters_idempotently`'s subprocess
  idiom in `test_battle2_command.py`): `python -m battle_engine agents
  create <agent-id>` followed by a second, separate `python -m
  battle_engine run --a-type <agent-id> --b-type <agent-id> --ticks 1`
  subprocess invocation succeeds (a fresh scaffold against itself is a
  legal, if uninteresting, Python-vs-Python match) and writes a replay.

**Duplicate protection**
- Creating the same `<agent-id>` twice: second call exits `2`, stderr names
  the existing path, and the first call's `agent.yaml`/`agent.py` content is
  byte-for-byte unchanged after the second (failed) call.
- Creating an `<agent-id>` that collides with a **file** (not a directory)
  already at that path is also rejected with exit `2`, and the file's
  content is unchanged.
- Creating an `<agent-id>` equal to a starter name whose directory
  `ensure_starter_agents` has already populated (`runner`) is rejected as a
  duplicate; creating one equal to a starter name that has *not* yet been
  materialized (calling this command against a brand-new data root
  directly, before any `bytefray agents`/`run`/`tournament` invocation has
  run `ensure_starter_agents`) succeeds — confirms §4's "no bespoke
  reserved-word list" decision is actually exercised both ways.

**Invalid/path-traversal IDs**
- Empty string, `..`, `../evil`, `a/b`, `a\\b`, a leading `-`, a name over
  the length cap, and a name containing a null byte or other non-printable
  character are all rejected with exit `2` and no filesystem mutation
  (assert `agents_dir` either doesn't exist afterward or is unchanged from
  its prior state).
- A name containing `..` as a harmless substring but not as a path segment
  (e.g. `not..actually..traversing`, mirroring the existing
  `test_agent_api.py` regression test's exact case) is currently expected
  to be **rejected by this command's stricter allow-list** even though
  `resolve_agent` itself would accept it for an *existing* agent — assert
  this explicitly as a documented, intentional behavior difference between
  "selecting an existing, already-vetted agent" (permissive) and "choosing
  a brand-new on-disk name" (conservative), not an oversight.

**Custom `BYTEFRAY_ROOT`**
- With `BYTEFRAY_ROOT` set to a `tmp_path` directory (and `BATTLE2_ROOT`/
  `BATTLE_ROOT` unset via `monkeypatch.delenv`), creation writes under that
  root, not the default/source-checkout root — mirrors `test_paths.py`'s
  precedence-testing idiom.
- With `BYTEFRAY_ROOT` unset but `BATTLE2_ROOT` set, creation writes under
  the `BATTLE2_ROOT` location (fallback precedence still honored,
  end-to-end through this new command, not just in `paths.py` unit tests).

**Filesystem failure behavior**
- Simulating an unwritable `agents/` directory (e.g. `monkeypatch` the
  temp-directory creation step to raise `PermissionError`, or — on POSIX
  only, `@pytest.mark.skipif(sys.platform == "win32", ...)` — actually
  `chmod` a directory read-only) results in exit `2`, a clear stderr
  message, no traceback, and no partially-created `agents/<agent-id>/` at
  the real (non-temp) path.
- Simulating a failure between writing the two files into the temp
  directory and the final rename (e.g. monkeypatching `os.rename` to raise)
  results in exit `2` and confirms `agents_dir / agent_id` does **not**
  exist afterward (the temp directory may remain, but the real path was
  never populated) — directly exercises §10's atomicity claim.

**Windows/POSIX path semantics**
- `tmp_path / "Writable Data With Spaces"` as the data root (mirroring
  `test_starter_agents.py`'s existing "paths with spaces" coverage) works
  identically to a plain path.
- Generated file content uses `\n` line endings regardless of platform
  (write with `encoding="utf-8"`, no platform-default newline translation
  surprises) so the byte-identical-across-IDs claim in §7 also holds
  byte-identical across platforms.

## 13. Design decisions needing human approval

1. **The exact `agent-id` allow-list (§4).** `^[A-Za-z0-9][A-Za-z0-9_-]*$`,
   max 64 characters, no normalization, is this spec's proposal, chosen to
   be strictly more conservative than what `discover_agents`/`resolve_agent`
   already tolerate for an *existing* agent. A narrower or differently-shaped
   allow-list (e.g. disallowing leading digits, requiring lowercase, a
   shorter cap) would also be defensible; this is a genuine judgment call
   with no existing project convention to defer to, and worth a second
   opinion before implementation.
2. **Resolved: omit `name`/`display` from the generated manifest entirely
   (§6).** Confirmed at implementation time: `name` is a recognized manifest
   field (`_spec_from_dir` validates its type when present), but it is
   never authoritative — agent identity is always the directory basename,
   and `name` is only ever echoed back as free-text `display` fallback.
   Adding `name: <agent-id>` to the generated manifest would create a
   second, driftable copy of identity that can silently disagree with the
   directory if either is later renamed, echoing exactly the field shape
   that was once a real path-traversal vector elsewhere in this codebase
   (`test_resolve_agent_rejects_a_name_that_escapes_the_agents_directory`).
   That is the "semantically dangerous enough to omit" case, so `name` (and
   `display`, for the same reason) is left out of the generated manifest.
   `docs/AGENT_AUTHORING.md`'s hand-written example is updated alongside
   this implementation to match the generated template and to point authors
   at the scaffold command first (see that file's changelog note).
3. **Resolved: `WRITE`, not `HALT`, as the template's placeholder action
   (§7).** This spec originally proposed `HALT` for being maximally simple
   and unambiguously "not yet a strategy." On review, that was rejected in
   favor of `WRITE` (matching `docs/AGENT_AUTHORING.md`'s existing example):
   an immediately-halting agent doesn't show a new author what an ordinary,
   valid, state-changing action looks like, which is the template's actual
   job, and the Agent API v1 surface makes `WRITE` no more complex to
   demonstrate than `HALT` — one extra `operand`/`value` pair, both already
   documented. §7 has been updated to generate the `WRITE`-based template
   shown there; `HALT` is retained inline in that section only as
   superseded context for why the simpler option was passed over.
4. **Exit code `2` for every failure category (§3.3),** rather than
   distinguishing, e.g., "duplicate" from "invalid ID" from "I/O error" with
   different codes. Proposed for consistency with the rest of the existing
   CLI (which does not distinguish either), but worth confirming no
   downstream tooling (CI scripts, the Designer's process-launch handling
   in `battle_engine.launchers`) would benefit from finer-grained codes
   before locking this in.
5. **New bundled resource directory `battle_engine/data/agent_template/`
   (§8)** versus embedding the two file bodies as string literals directly
   in `agent_scaffold.py`. The resource-file approach was chosen for
   consistency with `starters.py`'s existing pattern (and for easy manual
   inspection/editing of the template independent of Python source), but a
   reviewer favoring fewer moving parts for a two-small-file, no-templating
   case might reasonably prefer inline string constants instead — both are
   consistent with "avoid overengineering" and neither requires a
   `pyproject.toml` change either way (inline constants trivially need
   none; the resource-directory approach needs none either, per §8).
